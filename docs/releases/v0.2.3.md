# Aropyt v0.2.3 — Packaged Build Repairs

Two fixes. The first one made the packaged build nearly unusable; the second is
the bold text that should have been bold all along.

## The packaged build could not scroll, and source mode was blank

`npm run tauri dev` was fine. `npm run tauri build` was not: the editor would
not scroll in render mode, and switching to source mode gave an empty area.

The cause was a collision between Tauri's CSP generation and CodeMirror's
styling.

Tauri scans the built `index.html` and adds a `sha256` of every **inline**
`<style>` to the CSP `style-src`. The spec is specific about this: once
`style-src` contains a hash or a nonce, **`'unsafe-inline'` is ignored**. Our
policy had both.

CodeMirror does not ship its layout rules in a stylesheet. It injects a
`<style>` at runtime — `baseTheme` — and a runtime-injected sheet cannot have a
hash computed at build time. So the whole thing was blocked:

```
.cm-editor       display: block     (should be flex)
.cm-scroller     height: 168px      (editor is 721px tall)
```

A block-level editor with a content-height scroller is exactly what was
reported: no scrolling, and source mode with no layout at all.

The single inline `<style>` in `index.html` — the KaTeX host sizing rules —
moved into `styles.css`. That ships as a linked stylesheet, so no hash is
generated, and `style-src` is back to `'self' 'unsafe-inline'`.

`dev` never went through the hash step, which is why it stayed healthy and hid
the problem through the whole development cycle.

Verified against the packaged binary (`tauri build --debug --no-bundle`, loaded
over `tauri.localhost`):

```
before   editor.display: block   scroller: 168px    scrollHeight 168
after    editor.display: flex    scroller: 721px    scrollHeight 4766
         stylesheet alive, 184 rules
         source mode: content 860×5907, gutters 48px
```

## Bold text rendered as regular

The highlight style mapped `tags.strong` to `font-weight: 500`.

That reads as a reasonable "semi-bold", and on a system with a variable font it
would be. But Chinese fonts ship two weights — 400 and 700 — and CSS says a
request for 500 must fall back to 400 when nothing in that range exists. So
`**bold**` rendered as regular, always.

It also could not be fixed from the outside: the highlight span sits **inside**
the `.cm-md-strong` span the decoration adds, and an inner `font-weight` wins
over an outer one.

Headings were never affected because `heading1…6` already asked for 700. That
asymmetry — a bold heading containing bold text that is not bold — is what made
this look like a font problem rather than a single wrong value.

It is 700 now.

## Making 700 actually reach the bold file

While chasing the above, another gap turned up: with 700 requested on both the
heading and the inline span, the computed value was correct and the strokes
were still identical to regular.

The bold face is installed (`msyhbd.ttc`, 16 MB, in `C:\Windows\Fonts`), but a
CSS family name alone did not lead WebView2 to it.
`document.fonts.check('700 16px "Microsoft YaHei"')` returns `true` either way —
that call answers "does this family exist", not "does it have this weight".

Two `@font-face` rules now bind the family to both weights through `local()`,
which references installed fonts and ships nothing. `font-synthesis: weight` is
a fallback for systems where every lookup misses.

## Verifying

The two things reported:

- Scroll the editor in render mode — the scrollbar should move and the document
  should stay put under the toolbar.
- Switch to source mode — the text and line numbers should be there.

For bold, compare `**bold**` against a heading. Both should be visibly heavier
than body text.

## Note on this build

The CSP fix was confirmed against the packaged binary itself, over
`tauri.localhost` — the same path the installer uses.

The `@font-face` half could not be confirmed in the development environment:
the headless browser there has no Chinese font, so every weight — including
900 — renders identically.
